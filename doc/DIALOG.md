### 4. Коррекция скорости — вердикт: **текущий алгоритм некорректен**

#### 4.1. Где живёт коррекция

В боевой `motor_controller.ino` коррекции **нет** (комментарий «Без автопилота»).  
Логика синхронизации — только в `test_2_motors_rotation.ino`.

#### 4.2. Главный баг: смешение единиц измерения

```cpp
int32_t speed1 = actPos1 - lastPos1;          // тики энкодера за 20 мс
int32_t speed2 = actPos2 - lastPos2;          // тики энкодера за 20 мс

int targetSpeed1 = moveTarget + turnTarget;   // единицы ШИМ 0..255
int targetSpeed2 = moveTarget - turnTarget;   // единицы ШИМ 0..255

int32_t realDifference = speed2 - speed1;                 // тики
int32_t targetDifference = targetSpeed2 - targetSpeed1;   // ШИМ (= -2*turn)
int32_t error = realDifference - targetDifference;        // ❌ тики − ШИМ
```

При езде прямо (`turn = 0`) `targetDifference = 0`, и ошибка сводится к `speed2 - speed1` — это ещё осмысленно.

При повороте (`turn ≠ 0`) в ошибку подмешивается смещение порядка **сотен единиц ШИМ**, тогда как реальная разница скоростей в тиках обычно **десятки**. Интегратор `currentPWM_1` набирает ложный увод даже при правильном соотношении скоростей.

Численный пример (`move=150`, `turn=60`):

- целевые ШИМ: 210 и 90 → `targetDifference = -120`
- фактические скорости, пропорциональные цели: `speed1=42`, `speed2=18` → `realDifference = -24`
- `error = -24 - (-120) = +96` → каждый цикл +4.8 к ШИМ борта 1 → разгон интегратора

#### 4.3. Другие проблемы того же блока

1. **Асимметрия:** борт 2 всегда open-loop (`finalPWM_2 = targetSpeed2`), корректируется только борт 1. Допустимо как master/slave, но только при правильной ошибке в одних единицах.
2. **Знаки энкодеров на зеркальных моторах:** оба ISR одинаковые. Если при «вперёд» один борт даёт `+`, другой `−`, при `turn=0` ошибка огромна.
3. **Нет anti-windup** у `currentPWM_1` (есть только `constrain` на итоговом ШИМ).
4. **Программный ISR на одном канале A (CHANGE)** вместо аппаратного Encoder Mode (как в `test_1`) — хуже по джиттеру и нагрузке на CPU; для сравнения бортов ещё терпимо, но не оптимально.
5. **Нет калибровки «ШИМ → ожидаемые тики/период»** — нельзя сравнивать setpoint в ШИМ с измерением в тиках без шкалы.

#### 4.4. Что правильно делать вместо этого

**Вариант A (рекомендуемый): независимый speed-loop на каждый борт**

1. Задать целевые скорости в тиках/дТ:  
   `targetTicks1 = scale * (move + turn)`  
   `targetTicks2 = scale * (move - turn)`  
   (`scale` — эмпирический коэффициент тики↔ШИМ, либо таблица)
2. На каждом борту PI/PID:  
   `PWM_i += Kp*(targetTicks_i - speed_i) + Ki*∫...`
3. Знаки энкодеров выровнять константами `ENC_SIGN_1/2` (±1), один раз на стенде.

**Вариант B: sync только для прямолинейного хода**

- При `|turn| < ε`: минимизировать `speed1 - speed2` (оба в тиках).  
- При повороте: open-loop или полный вариант A.

**Вариант C (лучше долгосрочно):** аппаратные таймеры Encoder Mode для обоих бортов + отдельный UART на других пинах (не PB6/PB7, если они заняты энкодером).

#### 4.5. Нюанс стенда

Платформа вверх тормашками → нет одинаковой нагрузки гусениц о грунт. Разница скоростей на стенде ≠ поведение на полу. Тесты sync лучше подтверждать на земле / с одинаковой нагрузкой.

### 5. R_IS / L_IS — что это и как задействовать

Пользователь прав по сути: это **датчик тока** (current sense / diagnosis), а не отдельный «датчик нагрузки». Нагрузка оценивается **косвенно** через ток мотора.

По datasheet Infineon BTS7960:

- Пин `IS` отдаёт ток `IIS ≈ IL / kILIS`, где `kILIS ≈ 8500` (типично)
- На модулях IBT-2 / BTS7960B обычно уже стоят резисторы `RIS` (часто ~1–10 кΩ) на `R_IS` и `L_IS`
- `VIS = IIS × RIS = (IL / 8500) × RIS`
- В аварии (overtemp / short / current limit) пин уходит в режим fault и выдаёт повышенный ток `IIS(lim)` → напряжение резко растёт — можно детектить аварию

Важно:

- Ток измеряется через **активный high-side** ключ. При реверсе/другой половине моста «живой» другой `IS`.
- Практичный хак на многих IBT-2: **замкнуть R_IS и L_IS вместе** на один вход АЦП (если резисторы на плате уже к GND) — получать ток активного плеча на одном канале.
- Либо читать оба АЦП и брать `max(R_IS, L_IS)` / выбирать по направлению ШИМ.

Рекомендация для STM32F411 (АЦП до 3.3 В):

| Параметр | Значение |
| :--- | :--- |
| Пины (предложение) | `PA4` (борт1 IS), `PA5` (борт2 IS) — свободные ADC |
| Схема | проверить `RIS` на модуле мультиметром; при необходимости параллель для снижения Vis; делитель/стабилитрон 3.3 В для защиты АЦП |
| Частота опроса | 100–500 Гц с усреднением (ШИМ 2 кГц даёт шум) |
| Применение | ограничение тока / soft-fault, оценка нагрузки, диагностика заедания гусеницы |

Формула (после калибровки):

```text
IL ≈ (VIS / RIS_effective) * 8500
```

Калибровку лучше сделать амперметром на 1–2 известных токах — `kILIS` и реальный `RIS` на клонах плат гуляют.

## 2026-07-24 — Сессия 3: откат поломки команд веб-пульта

### Симптом
После добавления speed-loop ни одна команда веб-интерфейса не работает ожидаемо (раньше open-loop работал).

### Вероятные причины
1. `HardwareTimer` в `TIM_ENCODERMODE_TI12` на TIM1/TIM5 — нестандартный для Arduino API режим, риск конфликта с подсистемой `analogWrite`/таймерами.
2. PI без калибровки и/или без сигналов энкодера мог сильно уводить ШИМ от команды.

### Исправление
- Базовый ШИМ снова = `move±turn` (как в рабочей версии).
- Энкодеры через EXTI (`attachInterrupt` на A, чтение B), без захвата TIM1/TIM5 под Encoder Mode.
- Закрытый контур — только **ограниченный trim** (±40 ШИМ); при «молчании» энкодера trim = 0.
- Пины энкодеров те же: борт1 `PA0/PA1`, борт2 `PA8/PA9`.

### Проверка
1. Прошить STM32.
2. Команды FORWARD/LEFT/RIGHT/REVERSE/STOP должны снова совпадать с прежним поведением.
3. В Serial смотреть `spd=` — если нули при вращении, проверить проводку энкодеров; пока spd=0, поведение = open-loop.

## 2026-07-24 — Сессия 5: tot не накапливается при «правильной» коммутации

### Симптом
Пользователь проверил проводку; FORWARD даёт `tot≈0…1`, не растёт. Моторы крутятся (`pwm=150`).

### Интерпретация
На пинах энкодера нет устойчивого квадратурного сигнала (или он не доходит до EXTI). ±1 — шум подтяжки.

### Возможные причины
1. Неверная распиновка шлейфа (в docs конфликт: Motor wire.jpg = M+,VCC,A,B,GND,M− vs таблица docx = GND,C1,C2,VCC,M1,M2).
2. Нет питания энкодера / нет общей земли.
3. Сигналы на других жилах, чем A/B в схеме.

### Действие
Диагностическая прошивка: ISR на A **и** B, квадратурная таблица, `poll` (5 мс software edge count), `lvl`, `isr` счётчики. По логу FORWARD отличим «нет сигнала на пине» vs «EXTI не работает».

## 2026-07-25 — Сессия 9: проверка тока под нагрузкой

### Логи
- Без нагрузки: `I≈0.09,0.30`, `spd≈52/52`, trim ок.
- Нагрузка слева: `I≈1.14` слева, справа ~0.3; `spd` 22 vs 51 → PWM слева ↑ до 157.
- Нагрузка справа: `I` справа растёт 2.4→3.0 А; `spd` падает; PWM справа ↑ до 161.

### Вердикт
IS работает качественно (нагрузка на борту → рост тока этого борта). Контур скорости поднимает ШИМ отстающему борту.

Асимметрия холостого нуля 0.09 vs 0.30 и разный ток при «ручной» нагрузке (1.1 vs ~3 А) — разный оффсет/сила торможения и/или калибровка каналов. Абсолютная точность без амперметра не подтверждена.

### Правка

## 2026-07-25 — Сессия 10: ток после оффсетов

### Лог
- FORWARD: `I≈0.08–0.12` оба борта, `spd`/`pwm` в норме.

## 2026-07-25 — Сессия 11: STOP I≠0 и разбор readMotorCurrentA

### Симптом
После оффсетов 0.08/0.04 на STOP стабильно `I=0.12,0.15`.

### Причина
Оффсеты взяли из уже вычтенного лога STOP, а не из сырого тока. Исправление: `I_OFFSET = 0.20 / 0.19`.
